# V18 主项目整合

本次将 `engine-v17` 合并到 `/Users/xu/Code/AstraBall` 的 `main`。原项目起初没有 Git 仓库，先导入共同基线历史，再将原目录已有的青训、身体发育、租借和人才流动实现保存为 `pre-engine-merge`（e6e6ea1），随后执行三方合并。原有大型审计数据保留在磁盘，不重复写入 Git；测试需要的历史源码单独跟踪。

## 保留与接入

- 新游戏使用主项目 `playerRegistry`，保留每队每年三名青年、地方青训、皇家学院选秀、观察报告、租借、身体发育、训练负荷与角色机会评估。
- 接入空间站位、传球线路、位置职责、对手风格和临场调整。赛前选人保留主项目的角色匹配与轮换；临场加入同等实力的新鲜替补机会，玩家球队仍由玩家指挥。
- 合同、工资、转会、续约和解约接入同一注册表。青训提拔与流转在写入注册历史前检查预算并结算费用；租借期间保留母队合同，借入球队不能解除母队合同。皇家学院未签约青年不能通过合同页面绕过选秀。
- 青训中心、身体与成长面板、转会与合同页面同时保留。比赛档案使用真实动态球员身份。

## 存档与模型边界

- 含 `population` 的旧 worktree 生涯保留原人员和成长路径；新游戏使用 `playerRegistry`。两者按存档选择，不同时执行两套青年生成器。公共名单接口为合同与界面提供一致读写路径。
- 主项目和分支都曾使用比赛版本号 V6。主项目 V6 的完整依赖另行冻结为 `legacy/main-v6`，通过原有 AI 字段识别，继续按原规则完成未完赛比赛。分支 V6—V17 的历史路径继续保留。
- 新比赛使用 V18。人工控制下的动作模型与 V12 校准路径比较；AI 轮换有明确行为变化，不要求与旧 AI 产生同一事件序列。
- 浏览器新生涯与已载入的旧存档会接入财务。单独调用 `createSeason()` 的非财务青训审计仍可运行原模型；财务审计须调用 `ensureEconomy(s)`。已有财务存档自动继续财务流程。
- V16 的 15015 场与三十年报告保留为历史验收，不能当作此次合并版本已重跑的结论。可用 `BASELINE_REF=engine-v16 node scripts/football/verify-evolution.mjs` 核对原始源码。
