# 冷热球员档案设计

状态：独立设计提案，尚未实施。当前真实存档仍由 `store.js` 将完整赛季对象写入 IndexedDB；本文不搬移已有数据。它可以独立于[正式报名与预备队设计](正式报名与预备队设计.md)实施。

## 问题与范围

[20 季基线](青训长期验证.md)的完整赛季 JSON 从 41.8 MiB 增至 228.8 MiB。第 15 季分解为成长记录约 103.0 MiB、注册档案约 58.3 MiB、当季赛程约 14.8 MiB。这个数字是序列化后的逻辑体积，不是浏览器 IndexedDB 实际磁盘占用，也不是低内存设备性能测试结果。

当前 `mutate()` 每次读取当前完整赛季、`structuredClone` 后写回；跨季又保存新旧完整对象。退役球员虽然不再进入成长循环，仍存在注册与成长集合中。只压缩磁盘文件不能消除日常读写和复制成本；只归档比赛日志也没有处理最大来源。

目标是把“继续模拟必须同步访问的数据”与“查看历史时读取的数据”分开，保证身份、退役历史、历史赛果和完整导入导出。**冷档不是删除，不是自动退役，也不是每次刷新重新生成球员。** 本方案不承诺修复全部存档增长：现役人数仍在增长时，其当前状态仍需保存和模拟。

## 热数据与冷数据边界

| 数据 | 默认放置 | 原因 |
|---|---|---|
| 现役青年、一线、外租、预备队、仍可能签约的自由球员当前身份/属性/禀赋 | 热 | 成长、选人、招募可能每日读取；自由球员不因暂时无人关注而冻结年龄或成长。 |
| 当前训练计划、疲劳、近 7 日出场、周训练累计、伤停、禁赛、当前注册 | 热 | 影响下一次模拟，不能懒加载时才补算。 |
| 当前赛季累计、最近成长采样、观察报告最新证据 | 热 | 日常 UI 和观察更新直接需要。若现有算法依赖至少 90 日趋势，保留足够窗口；不能任意只留 7 日。 |
| 活动比赛状态、随机游标、资格快照、待处理流转 | 热 | 恢复必须立即完整，进行中比赛引用的球员禁止归冷。 |
| 已结束年份的年度成长、旧观察、完整注册/训练事件、历史比赛明细 | 冷 | 不参与当前数值推进，按球员或赛季查询。算法确实需要的摘要保留在热层。 |
| 已退役球员的最终完整档案及其旧成长记录 | 冷 | 不再推进数值；身份和关键生涯索引持续可查。 |
| 历史赛季状态 | 冷、不可变 | 用于档案查看、独立分支和完整导出，不能被当前球员的新状态覆盖。 |

热层必须明确列出所有参与模拟的字段白名单。现行 `development.records` 中的 `attributes/seasonAttributes/dose/weekMinutes/weekChallenge/healthyDays` 均不能因名称像历史就移走。`annual` 可按年份移出，现行 `history` 保留完整算法窗口；每个已冷却片段在冷层仍可重建。

身份目录保留 `playerId/name/searchKey/primaryPosition/ageOrigin/lifecycle/retiredAt/lastKnownClubId/lastKnownCA/profileRef/historyRefs`。目录可以分页持久化，不必把所有退役摘要永久加载到内存。实时视图中的 `registeredPlayer()` 不能把缺少热对象当成“球员不存在”；必须区分现役已加载、冷档待读取、不存在与损坏。

原始职业球员目前来自静态 `footballTeams`，归冷与导出时必须包含其身份快照或锁定并随包提供对应世界数据版本；不能假定新安装的应用静态名单永远相同。

## 建议持久化结构

IndexedDB 升级为新的数据库版本，仅在 `onupgradeneeded` 创建表和索引；不要在升级事务内展开数百 MiB 的旧档迁移。建议容器如下，字段版本与游戏规则版本分开。

| 表 | 键与内容 | 可变性 |
|---|---|---|
| `worldHeads` | `worldId → {formatVersion,generation,revision,currentSeason,manifestRef,previousManifestRef}` | 只有提交事务可以移动当前指针。旧档补固定 `worldId`，年份不再是跨存档唯一键。 |
| `manifests` | 内容 ID → 热状态分片引用、身份目录引用、冷块目录引用、历史赛季引用、完整性摘要 | 不可变；引用组成一个可恢复版本。 |
| `stateChunks` | 内容哈希 → 当前赛季/球员当前状态分片 | 内容不可变，修改后产生新片；未变分片跨版本复用，避免每次重写全体球员。 |
| `archiveBlocks` | 内容哈希 → `{schemaVersion,codec,byteLength,checksum,payload}` | 保存退役完整档案、历史片段或已封存赛季数据；不可原地覆盖。 |
| `playerDirectoryPages` | 内容 ID → 身份摘要及档案引用 | 按页查询与版本引用，保持历史赛季的身份视图可重现。 |
| `storageJobs` | `jobId → {kind,sourceWorld,sourceRevision,stage,cursor,stagedRefs,verification}` | `kind` 区分迁移、分批提交、导出；可中断续做，并在完成前保护暂存块不被回收。 |
| `meta` | 当前世界 ID、能力与版本信息 | 不装入完整档案。原 `seasons/meta` 在迁移期保留为旧格式来源。 |

分片以俱乐部/球员 ID 分组并设有界字节目标，建议原始块 0.5–2 MiB 起步后测量。不能仅以固定球员数分块导致某名球员的长历史产生超大块。超长单人生涯按年份继续分片，并维护严格顺序与唯一事件 ID。压缩可选，`codec:'json'` 必须是可用降级；压缩是体积优化，哈希与结构校验仍独立进行。

第一阶段允许热层继续保持一个当前赛季对象，仅把冷历史从日常对象分离；后续再切分热状态，不能把两步收益混报。所有存储读写通过一个持久化适配层，纯模拟代码继续接收已准备好的热状态，不在选人循环中异步读 IndexedDB。

## 归冷与回读生命周期

赛季封存时，将年度成长、固定注册/观察事件片段、历史赛果写成不可变冷块。热层留下当前数值、累计摘要和引用。封存前后下一季输入须逐字段等价；职业分钟、首秀日期、退出原因等不能通过丢历史来重新估算。

退役事件提交后先结束其成长与健康状态，在没有活动比赛、未结算流转或当前事务依赖时归冷。完整最终档案、当时注册历史、体格、属性、发展上限和观察证据写入冷块；身份目录保留可检索摘要。隐藏 PA 仍由公开档案过滤，不能因为读取的是历史块就直接展示。

当前规则无复出时，不新增复活机制。未来明确支持复出，需完整回读并校验旧档，在事务中恢复热状态，按新的复出规则建立起点；不能把冷档缺失当作随机生成一个同名球员。

建议读取接口拆为：`getActivePlayer()` 同步供模拟；`queryPlayerDirectory()` 分页搜索；`loadPlayerArchive()` 异步读取生涯；`loadSeasonView()` 读取指定历史版本；`materializePortableSave()` 构建可移植完整导出。冷读返回独立视图对象，不能把整份历史塞回日常热状态导致下次保存又全部复制。

青训“培养记录”、选秀名单、退役档案和历史比赛链接按同一 ID 解析。页面先显示目录摘要与加载状态，再补生涯；加载失败显示可重试错误，不能显示“无此球员”或回退成名单第一人。取消导航可取消展示，但已校验只读块可进有界 LRU 缓存；清缓存不影响持久化内容。

## 事务、并发与故障恢复

1. 在持久化锁内读取 `head.revision`，准备下一热状态及待归冷块。计算哈希、压缩和结构校验在事务外完成，不能在 IndexedDB 事务中等待网络、定时器或异步摘要导致事务自动结束。
2. 大量新块可分批写入为未被提交清单引用的暂存内容。先建立 `storageJobs` 并保护其引用；每块及其暂存引用在同一批次事务写入，防止并发清理误删。每块写入后检查内容哈希、长度和 schema；保存完整清单前验证所有引用存在。暂存进度只是迁移/提交作业状态，不代表游戏已推进。
3. 最终短事务读取并比较旧 `head.revision`，写入清单并切换 head，关联必要热状态、冷档索引和元信息。若版本已变化则整次提交失败，重新加载后重算；禁止丢掉对方写入。
4. 只有事务 `oncomplete` 后 UI 才显示已保存并替换 `current`。配额不足、标签关闭或断电发生在提交之前，旧 head 仍有效；提交之后则新 head 引用的数据已经完整。不能先删除热字段再异步补冷档。
5. 保留最近有效清单及其引用。孤立暂存块只在确认没有任何当前世界、历史赛季、备份、导出快照或进行中作业引用后清理。以引用可达性做垃圾回收，不凭文件年龄删除。作业是否废弃须在事务中复核，不只按超时猜测另一个标签已死亡。

`navigator.locks` 可减少冲突，但正确性必须由最终事务中的 revision 比较保证。没有 Locks API 时也可安全提交；页面内 `busy` 不是跨标签锁。数据库 `versionchange` 应关闭旧连接，`blocked` 提示另一标签需重新加载，不强行清空数据库。

冷块读失败区分：暂时读取异常可重试；校验失败进入损坏状态。若受影响块是活动世界继续模拟的必要状态，暂停写入并提供恢复上一有效版本或导入备份。若仅一份历史档案损坏，当前独立热模拟可继续，但标记存档存在完整性问题，完整导出必须说明失败并不得标为完整。不得用摘要补造丢失属性或把缺块当空历史；保留坏块用于诊断与可恢复导出。

## 旧档迁移

先完整校验旧档并记录源格式、源 revision、字节摘要和迁移作业 ID。转换采用固定排序和确定性规则，不新增球员、不变更退休状态、不改变年龄或能力，不重放已完成比赛。旧代码依赖静态的初始球员必须被身份目录覆盖。

按球员与历史赛季分批复制到新表，逐批持久化 cursor；中断后从已核验部分继续，重复块按哈希去重。所有清单引用、人数、累计分钟、历史事件、当前模拟必要字段核对通过后，短事务切换 head 并保留旧档只读副本。整个迁移期间旧档仍是唯一可继续使用的版本；不能允许同一源 revision 一边推进、一边完成过时迁移。若用户继续游戏，作业应暂停或基于新 revision 重启。

额外空间不足时，不能为了迁移先删旧档。保留原格式可用状态，提示可导出备份和释放空间；仅在完成新格式并确认可恢复后再提供清理旧副本操作。新格式不是旧客户端可写格式：旧客户端遇到较新版本应拒绝写入而非降级覆盖。需要兼容导出时显式物化成受支持旧格式，并报告新功能不可表达的限制，不能默默丢字段。

## 完整导入、导出与审计档的区别

真实保存发生在 IndexedDB，跨引用事务和恢复流程必须在浏览器中验证。现有 `artifacts/academy-world/...json.gz` 是开发审计快照，当前 gzip 并未作为浏览器存档格式实施；不能用审计文件变小证明日常保存已优化。

完整导出先固定一个不可变 manifest 快照，再逐块流式读取其可达数据，写入自描述容器：格式/规则版本、世界 ID、文件清单、每块长度与 SHA-256、所有身份与冷档、历史赛季、当前热状态、活动比赛、世界数据版本或嵌入快照。只打包 head 或目录是不完整导出。快照被导出引用期间，不得被垃圾回收。

导入在新 worldId 的暂存空间中检查格式兼容、大小上限、块校验、ID 与引用完整性、历史时间关系及活动比赛恢复条件。全部通过后原子切换为一个独立世界；不覆盖当前存档，不按同名球员合并，不与旧 worldId 的相同 playerId 混淆。失败只留下可清理暂存作业，当前世界不变。

无流式文件写出能力时提供分卷导出，主清单列齐各卷并校验，不退回创建巨型内存字符串。压缩 API 不可用时输出未压缩块。压缩格式未知时拒绝导入并保留原文件，不误判为零球员。实际是否能容纳某个存档需测量配额和运行内存，不能承诺浏览器永不回收本地数据。

## 验收案例

1. 归冷前后使用同一个固定快照推进完整一季，规范化后的赛果、属性、伤停、成长累计、注册状态完全一致；存储引用和压缩字节可不同。
2. 退役原始球员与退役新生代均可从搜索、选秀记录、历史比赛进入完整生涯；名字、位置、最终能力与历史归属不变，PA 不公开。
3. 选中几十年前的赛季，不读取当前球员状态替代当年的属性、名字或归属；历史档案不因当前转会而改写。
4. 缓存清空后完整冷读恢复；离线浏览不需要网络。缺块与损坏块明确报错，绝不随机重建。
5. 在暂存写入、最终指针提交前后、跨季封存和退役归冷阶段分别注入配额/事务失败、关标签；恢复后只有旧完整版本或新完整版本，不出现半份球员。
6. 两标签并发操作以及无 Locks API 环境下，过期 revision 提交不能覆盖新状态；升级阻塞不删库。
7. 活动比赛保存/恢复/继续与归冷前相同；被活动比赛引用的球员不提前归冷。
8. 完整导出→清空测试数据库→导入→查看退役历史并继续推进，与导出前完整逻辑状态一致；丢失一卷或任一块校验错误时不提交导入。
9. 迁移反复中断、重复执行、源 revision 变化、空间不足均不损坏源档；包含静态初始球员与已有超过 4,000 条生涯事件的情况。原本已被旧版删除的事件不伪造恢复，保留可用的注册历史并标明原口径。
10. 单独测量冷块数量、热对象逻辑字节、IndexedDB 占用、事务时长、页面保存 P50/P95、加载峰值内存和档案首屏延迟；固定设备与快照比较，不把 gzip 比例当延迟结论。

## 分阶段实施

第一阶段只增加存储适配层与格式检测，维持完整对象读写，补事务失败、版本冲突、活动比赛及导出导入测试，建立固定快照性能基线。

第二阶段建立身份目录与异步历史查询，再将退役完整档案和已结束年份的成长/注册历史归冷。先做纯读取迁移预演，核对所有计数和逻辑字段；通过后才启用 head 切换。此阶段不改变现役计算算法，也不承诺热数据达到固定大小。

第三阶段拆分热状态，按修改集保存球员、赛事和注册分片；旧赛季使用不可变清单复用未变块。给结构克隆、哈希和压缩设置有界任务，避免全部搬到主线程一次完成。

第四阶段开启流式完整导出导入、可达性垃圾回收和独立多赛季保真测试。最后才讨论更激进的现役懒加载；自由球员或长期预备队若仍参与模拟，就不能通过归冷停止成长。

是否达标以逻辑保真、故障恢复和实测交互成本共同判断，不以“文件变小”单项验收。报名/预备队方案新增字段只需进入相应的热字段与归档 schema，不要求两套方案同时上线。
