# AstraBall 游戏体系与界面架构

本次整理以现有游戏规则和存档为准，不改写世界设定、经济模型或赛事结果。目标是让玩家清楚自己在哪、能做什么、下一步去哪。

## 1. 游戏主循环

选择俱乐部 → 检查球队与预算 → 调整阵容 / 培养 / 转会 → 查看赛程并推进日期 → 备战与执教 → 赛果、体能与财政更新 → 继续赛季 → 年度结算与下一赛季。

经理首页承担待办与下一场比赛入口。比赛中心集中展示赛程、日历、积分榜和签表。世界资料提供地理、俱乐部、人物与地方足球背景，支持经营决策。

导航顺序固定。当前页以紫色底、左边线和文字共同标记。桌面保留所有文字，窄屏通过“菜单”展开分组；不再缩成无名称的奖杯列表。

“俱乐部总览”和“球队阵容”默认回到执教球队；查看对手不会改变默认球队。未接手时仍可浏览默认俱乐部，侧栏明确显示“尚未选择执教球队”。

## 3. 详情与上下文

- 球员不是顶层固定人物入口。从阵容、转会、青训、关注名单或地区资料进入具体球员。已有完整竞技档案与出身/家族档案通过链接相互连接。
- 阵容中的战术、友谊赛属于球队操作；正式执教比赛属于比赛中心。两类比赛不能混为一谈。
- 俱乐部月历与赛程是比赛中心按球队过滤的视图，复用同一赛历和赛果。
- 赛制规则是静态规则资料；积分榜、赛果、签表来自赛季状态。
- 历史页展示归档结果，比赛中心展示当前或所选赛季。年份与当前游戏日期分开标注。
- 球员详情使用详情标题和返回入口，不错误高亮“关注名单”。

## 4. 状态与数据归属

| 层 | 当前文件 | 责任 |
| --- | --- | --- |
| 世界与规则 | world.js、geography/、competitions/catalog.js、club-profiles.js | 地理、身份、关系、赛事规则与俱乐部初始资料 |
| 赛季与业务 | competitions/runtime.js、calendar.js、career.js、market.js、development.js、youth.js 及经济模块 | 成员、赛程、竞技成长、交易、经营与年度结算 |
| 单场模拟 | football/engine.js、coach.js、ai-team.js | 阵容输入、比赛过程、比赛结果 |
| 存档与变更入口 | competitions/store.js | 加载、锁定、复制状态、执行业务变更、校验与写入 IndexedDB |
| 页面展示 | app.js、navigation.js、各 ui.js、hub.js、presentation.js、atlas.js | 路由、页面生命周期、查询与格式化、用户操作 |

正式比赛由赛历选择比赛，比赛引擎产出结果，赛季模块合并统计和状态，再由存档层保存。页面不得自行发明另一个积分榜、预算或日期来源。

关注名单单独存在 localStorage；正式赛季存于 IndexedDB。切换页面不推进日期、不修改合同、不重新创建赛季。

## 5. 统一视觉与样式边界

- theme.css：唯一全局色板。深蓝背景、统一中性面板、紫色操作与选中态。
- app-shell.css：唯一应用外框。品牌、三组导航、页头、正文边距、移动菜单。
- style.css / atlas.css / football.css / competitions 下样式：各自内容布局。
- management-design.css：参考图对应的管理界面、密集表格、赛历和比赛界面呈现。
- 已清理旧模块对 sidebar、nav-item、workspace、topbar 的独立覆盖。组件不得随路由改变全局主题或隐藏菜单名称。
- 地图区域色、球衣色、球场绿色表达对象本身；胜负、体能、伤病使用状态色。它们不影响应用外框。
- 数字、人物和队名是主体。图标只在有明确语义时出现，导航不使用重复奖杯占位。

## 6. 已知边界与后续演进

现有竞技球员详情与世界人物档案仍是两个相连视图，分别由 football/ui.js 与 app.js 负责；本次统一归属与导航，未改写数据模型。若后续合成同一球员页，推荐内部使用“竞技 / 生涯 / 关系”标签，仍以球员 ID 关联。

经济系统已有多个细分模块。展示层应继续区分俱乐部可操作财政与世界经济查询，避免把宏观资金表放进经理待办。

本次保留原 hash 链接与存档格式。新增导航配置及界面色板不需要存档迁移。
